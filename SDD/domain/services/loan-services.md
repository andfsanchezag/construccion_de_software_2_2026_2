# Loan Services

## Introduction

This document defines the services belonging to the **Loan** subdomain of the Banking Information Management System.

The services in this subdomain are responsible for managing the lifecycle of loans requested by customers, from the initial application through evaluation, approval or rejection, disbursement, cancellation, and closure when applicable.

Loans are represented by the `Loan` Domain Model and inherit from `BankingProduct`.

```text
BankingProduct
      │
      └── Loan
```

A loan is a banking product associated with a `Customer`.

Its lifecycle generates business operations that must be traceable through the `Operation` and `AuditLog` Domain Models.

The services described in this document define the conceptual behavior of the Loan subdomain.

Implementation details such as REST contracts, persistence mappings, JPA entities, SQL queries, MongoDB documents, HTTP clients, and infrastructure-specific mechanisms must be documented separately.

---

# Domain Model Context

A `Loan` represents a credit product requested by a customer.

Conceptually:

```text
BankingProduct
      │
      └── Loan
             │
             ├── applicant : Customer
             ├── loanType : LoanType
             ├── requestedAmount : BigDecimal
             ├── approvedAmount : BigDecimal
             ├── interestRate : BigDecimal
             ├── termInMonths : Integer
             ├── loanStatus : LoanStatus
             ├── approvalDate : LocalDate
             ├── disbursementDate : LocalDate
             └── destinationAccount : BankAccount
```

The applicant must be represented using the `Customer` Domain Model:

```text
Loan.applicant : Customer
```

The destination account must be represented using the `BankAccount` Domain Model:

```text
Loan.destinationAccount : BankAccount
```

The Domain Model must not replace these relationships with primitive identifiers such as:

```text
String customerId
String accountId
```

Persistence adapters are responsible for translating Domain relationships into their infrastructure representation.

---

# Value Objects Used by Loan

The Loan subdomain relies on the following Value Objects defined in the Domain Value Objects specification.

```text
Loan
 │
 ├── loanType       : LoanType
 ├── loanStatus     : LoanStatus
 ├── applicant      : Customer
 │      ├── status  : CustomerStatus
 │      └── role    : SystemRole
 │
 └── destinationAccount : BankAccount
        ├── accountType   : AccountType
        ├── accountStatus : AccountStatus
        └── currency      : Currency
```

The acting `User`, when applicable, also exposes:

```text
User
 ├── status : UserStatus
 └── role   : SystemRole
```

Business operations generated by Loan services use:

```text
Operation.operationType : OperationType
```

Relevant operation types include:

```text
LOAN_APPLICATION
LOAN_APPROVAL
LOAN_REJECTION
LOAN_DISBURSEMENT
LOAN_PAYMENT
LOAN_OVERDUE
LOAN_CANCELLATION
```

---

# Value Object Validation Principles

Value Objects are part of the Domain Model and must not be treated as arbitrary strings.

For example:

```text
LoanType
LoanStatus
CustomerStatus
UserStatus
AccountStatus
AccountType
Currency
OperationType
SystemRole
```

must represent controlled business values.

The service must not validate them through arbitrary string comparisons such as:

```java
loan.getLoanStatus().equals("APPROVED");
```

Instead, the Domain Model must work with the corresponding Value Objects.

Conceptually:

```java
loan.getLoanStatus().equals(LoanStatus.APPROVED);
```

or, preferably, through expressive Domain behavior:

```java
loan.isApproved();
loan.canBeDisbursed();
loan.canBeCancelled();
```

The exact implementation mechanism is an implementation decision, but the business concept must remain inside the Domain.

---

# DomainCatalog Rules

All catalog Value Objects inherit conceptually from:

```text
DomainCatalog
```

with:

```text
code
name
description
```

Catalog Value Objects must be:

* Immutable.
* Comparable by value.
* Restricted to valid business values.
* Identified by a unique business code.
* Independent from persistence technology.
* Independent from REST representation.

A Loan service must never create arbitrary catalog values such as:

```text
new LoanStatus("ANY_VALUE")
```

unless the Domain provides a controlled factory capable of enforcing catalog invariants.

---

# Monetary Representation

All monetary attributes in the Loan Domain Model remain represented as:

```text
BigDecimal
```

No `Money` Value Object is introduced by this specification.

The following attributes remain `BigDecimal`:

```text
requestedAmount : BigDecimal
approvedAmount  : BigDecimal
```

`interestRate` is also represented as:

```text
BigDecimal
```

because it is a business numeric value rather than a monetary amount.

---

# Monetary Validation Rules

The Domain must enforce the following invariants.

## Requested Amount

```text
requestedAmount != null
requestedAmount > 0
```

The amount must represent a positive financial value.

Zero or negative requested amounts are invalid.

---

## Approved Amount

Before approval:

```text
approvedAmount == null
```

or, if the business process allows a preliminary value, it must still satisfy the Domain constraints.

When a loan is approved:

```text
approvedAmount != null
approvedAmount > 0
```

Unless the business rules explicitly permit otherwise:

```text
approvedAmount <= requestedAmount
```

The approval service must not accept an independent `BigDecimal approvedAmount` parameter.

The amount must belong to the `Loan` Domain Model.

---

## BigDecimal Comparison

Because Java `BigDecimal.equals()` considers scale, Domain numerical comparisons must not rely on it when comparing monetary magnitude.

Conceptually:

```java
amount.compareTo(BigDecimal.ZERO) > 0
```

rather than:

```java
amount.equals(BigDecimal.ZERO)
```

---

## Monetary Precision

The Domain must define a consistent precision and scale policy for:

```text
requestedAmount
approvedAmount
interestRate
```

This policy must be applied consistently during:

* Validation.
* Calculation.
* Persistence mapping.
* Disbursement.
* Payment processing.

Floating-point types such as:

```text
double
float
```

must never be used for monetary values.

---

# Interest Rate Validation

`interestRate` remains:

```text
BigDecimal
```

The Domain must validate:

```text
interestRate != null
interestRate >= 0
```

The maximum permitted rate, precision, scale, and LoanType-specific rate rules must be defined by the corresponding business policies.

If interest-rate rules become sufficiently complex, a future `InterestRate` Value Object may be introduced.

This specification does not require that Value Object.

---

# Loan Term Validation

`termInMonths` remains:

```text
Integer
```

The Domain must validate:

```text
termInMonths != null
termInMonths > 0
```

Additional restrictions may depend on:

```text
LoanType
```

For example:

```text
LoanType
    │
    ├── PERSONAL
    ├── MORTGAGE
    ├── VEHICLE
    └── BUSINESS
```

Each LoanType may define:

* Minimum term.
* Maximum term.
* Minimum amount.
* Maximum amount.
* Interest-rate constraints.
* Customer-type restrictions.
* Additional eligibility requirements.

These rules belong to the Domain.

---

# Currency Validation

A Loan involving monetary values must have a well-defined currency.

If `BankingProduct` already provides:

```text
currency : Currency
```

the Loan inherits that value.

If `BankingProduct` does not contain currency, the Loan model must be extended to explicitly represent its currency.

A loan with monetary amounts but without an identifiable currency is incomplete for a multi-currency banking system.

The Domain must validate:

```text
Loan.currency != null
```

when currency is part of the applicable model.

---

# Currency Compatibility

During disbursement:

```text
Loan.currency == destinationAccount.currency
```

must hold unless the business explicitly supports foreign-exchange conversion.

If currencies differ and no FX business capability exists:

```text
CurrencyMismatchException
```

must be raised.

The Loan service must not silently convert currencies.

If currency conversion is introduced in the future, it must be represented through an appropriate Domain Policy and Output Port.

---

# CustomerStatus Validation

The applicant is represented by:

```text
Loan.applicant : Customer
```

The Customer's status is:

```text
Customer.status : CustomerStatus
```

For normal Loan processing, the applicant must satisfy:

```text
CustomerStatus.ACTIVE
```

The following states must not automatically be treated as equivalent:

```text
ACTIVE
INACTIVE
BLOCKED
```

Therefore:

```text
INACTIVE != BLOCKED
```

and the business rules may define different consequences for each.

Unless explicitly specified otherwise:

```text
INACTIVE → cannot initiate new loan applications
BLOCKED  → cannot initiate new loan applications
ACTIVE   → may proceed subject to eligibility rules
```

---

# UserStatus Validation

When a Loan operation is performed by a User, the service must validate:

```text
User.status
```

The normal requirement is:

```text
UserStatus.ACTIVE
```

A user with:

```text
INACTIVE
BLOCKED
```

must not execute protected Loan operations.

User status is independent from Customer status.

For example:

```text
Customer.status = ACTIVE
User.status     = BLOCKED
```

does not authorize the User to execute an operation.

Likewise:

```text
Customer.status = BLOCKED
User.status     = ACTIVE
```

does not make the Customer eligible.

---

# SystemRole Validation

Roles are represented by:

```text
SystemRole
```

Relevant roles include:

```text
NATURAL_CUSTOMER
BUSINESS_CUSTOMER
TELLER_EMPLOYEE
COMMERCIAL_EMPLOYEE
BUSINESS_OPERATOR
BUSINESS_SUPERVISOR
INTERNAL_ANALYST
```

Authorization must validate both:

```text
User.status
User.role
```

A role alone is insufficient.

For example:

```text
User.role = INTERNAL_ANALYST
User.status = BLOCKED
```

must not authorize loan approval.

---

# Important SystemRole Modeling Rule

`NATURAL_CUSTOMER` and `BUSINESS_CUSTOMER` represent customer classifications more than conventional authorization roles.

If `SystemRole` is also defined as the authorization role of a `Person`, the Domain must establish how these values relate to:

```text
NaturalCustomer
BusinessCustomer
```

The system must not use `SystemRole` as a substitute for determining the actual Customer subtype.

For Loan eligibility, the authoritative object is:

```text
Customer
```

and its concrete specialization:

```text
NaturalCustomer
BusinessCustomer
```

When a rule depends on the type of customer, the service must use the Customer Domain Model rather than inferring customer type exclusively from a role string.

---

# LoanType Validation

Valid Loan Types are:

```text
PERSONAL
MORTGAGE
VEHICLE
BUSINESS
```

The service must validate that:

```text
loan.loanType != null
```

and that it represents a valid controlled `LoanType`.

The service must not accept arbitrary strings.

---

# LoanType-Specific Eligibility

The following rules must be represented as Domain policies or specifications when applicable.

```text
LoanType
    │
    ├── PERSONAL
    ├── MORTGAGE
    ├── VEHICLE
    └── BUSINESS
```

Potential business constraints include:

```text
Customer type
Amount range
Term range
Interest rate range
Destination account requirements
Collateral requirements
Income requirements
Existing debt constraints
```

The current specification does not define exact numerical thresholds.

Therefore, services must not invent such thresholds.

They must delegate them to explicit Domain Policies/Specifications once the business rules are defined.

---

# AccountType Validation

The destination account exposes:

```text
BankAccount.accountType : AccountType
```

Valid values include:

```text
SAVINGS
CHECKING
BUSINESS
```

The Loan service must validate the account type when LoanType-specific disbursement rules require it.

For example:

```text
BUSINESS Loan
    ↓
may require
    ↓
BUSINESS Account
```

Such restrictions must be explicit Domain rules and must not be inferred from the database.

---

# AccountStatus Validation

The destination account exposes:

```text
BankAccount.accountStatus : AccountStatus
```

Valid states are:

```text
ACTIVE
BLOCKED
CLOSED
```

A Loan disbursement requires:

```text
AccountStatus.ACTIVE
```

The following states must reject disbursement:

```text
BLOCKED
CLOSED
```

The Loan service must not credit an account that cannot receive operations.

---

# Destination Account Ownership

The Loan service must validate the relationship between:

```text
Loan.applicant
```

and:

```text
Loan.destinationAccount
```

The service must not assume that the relationship is valid merely because both Domain Models are present.

Where the business rule requires the destination account to belong to the applicant, the service must validate:

```text
Loan.applicant
        │
        ▼
BankAccount.owner
```

The authoritative `BankAccount` may be retrieved through the corresponding Output Port when the supplied Domain Model is incomplete or stale.

---

# Loan Status Value Object

The Loan uses:

```text
LoanStatus
```

The supported states are:

```text
UNDER_REVIEW
APPROVED
REJECTED
DISBURSED
OVERDUE
CANCELLED
```

The Domain must be the authority for valid transitions.

---

# Loan Lifecycle

The lifecycle is:

```text
                 ┌──────────────► REJECTED
                 │
UNDER_REVIEW ────┼──────────────► CANCELLED
                 │
                 ▼
              APPROVED
                 │
                 ├──────────────► CANCELLED
                 │
                 ▼
             DISBURSED
                 │
                 ▼
              OVERDUE
                 │
                 ▼
             CANCELLED
```

A separate `CLOSED` state is not included in the current LoanStatus catalog.

Therefore:

```text
CloseLoanUseCase
```

must not be used unless `CLOSED` is explicitly added to `LoanStatus` and its lifecycle is formally defined.

The current service is therefore:

```text
Cancel Loan
```

with:

```text
CancelLoanUseCase
```

---

# State Transition Rules

The Domain must enforce:

```text
UNDER_REVIEW → APPROVED
UNDER_REVIEW → REJECTED
UNDER_REVIEW → CANCELLED

APPROVED → DISBURSED
APPROVED → CANCELLED

DISBURSED → OVERDUE

OVERDUE → CANCELLED
```

Invalid transitions must raise:

```text
InvalidLoanStatusTransitionException
```

The persistence layer must never determine whether a transition is valid.

---

# Lifecycle Ownership

The service must never allow an external caller to arbitrarily assign:

```text
loanStatus
approvalDate
disbursementDate
```

For example, a request must not be trusted merely because it contains:

```text
loanStatus = APPROVED
```

The service must establish the correct initial state through Domain behavior.

Likewise:

```text
approvalDate
```

must be established when the Domain performs the approval transition.

And:

```text
disbursementDate
```

must be established when the Domain performs the disbursement transition.

---

# Standard Loan Service Pattern

Every state-changing Loan service must follow the following conceptual pattern:

```text
1. Receive Domain Models
        │
        ▼
2. Retrieve authoritative state when necessary
        │
        ▼
3. Validate User
        │
        ▼
4. Validate Customer
        │
        ▼
5. Validate User-Customer relationship
        │
        ▼
6. Validate Loan
        │
        ▼
7. Validate Value Objects
        │
        ▼
8. Validate Loan status
        │
        ▼
9. Validate operation-specific business rules
        │
        ▼
10. Execute Domain behavior
        │
        ▼
11. Persist Domain Model
        │
        ▼
12. Create Operation
        │
        ▼
13. Create AuditLog
```

Not every service requires every step.

Only relevant validations must be executed.

The service must not introduce artificial validation use cases such as:

```text
ValidateUserService
ValidateOwnershipService
ValidateLoanStatusService
ValidateAccountService
```

when those validations are part of a larger cohesive business operation.

---

# Authoritative State Rule

For state-changing operations, the Loan supplied to the service represents the business context but must not automatically be considered the authoritative persisted state.

When required, the service retrieves the authoritative Loan through:

```text
LoanRepository
```

Conceptually:

```text
Incoming Loan
     │
     ▼
LoanRepository
     │
     ▼
Authoritative Loan
     │
     ▼
Business Validation
     │
     ▼
Domain Behavior
```

This prevents stale Domain Models from causing invalid state transitions.

# 1. Request Loan

## Description

Creates a new loan application for a Customer.

The loan enters:

```text
UNDER_REVIEW
```

The caller must not arbitrarily determine the initial lifecycle state.

---

## Input

```java
Loan request(Loan loan);
```

The Domain Model must contain:

```text
Applicant
LoanType
RequestedAmount
Term
DestinationAccount when applicable
Currency when applicable
```

---

## User Validation

If the request is initiated by an authenticated User, the service must validate:

```text
User.status == ACTIVE
```

and the appropriate authorization rule.

If the request is customer-initiated, the service must validate:

```text
User
   │
   ▼
Customer
   │
   ▼
Loan.applicant
```

The requesting Customer must correspond to the applicant.

---

## Customer Validation

Validate:

```text
loan.applicant != null
loan.applicant.status != null
loan.applicant.status == CustomerStatus.ACTIVE
```

Additional Customer information must be obtained through:

```text
CustomerRepository
```

only when it is not already available in the Domain Model.

---

## LoanType Validation

Validate:

```text
loan.loanType != null
```

and ensure that the value belongs to the supported `LoanType` catalog.

---

## Requested Amount Validation

Validate:

```text
requestedAmount != null
requestedAmount > 0
```

LoanType-specific amount restrictions must also be evaluated.

---

## Term Validation

Validate:

```text
termInMonths != null
termInMonths > 0
```

LoanType-specific term restrictions must also be evaluated.

---

## Destination Account Validation

When a destination account is required:

```text
destinationAccount != null
```

The account must:

```text
exist
be ACTIVE
allow credit operations
satisfy ownership rules
satisfy AccountType rules
satisfy Currency rules
```

---

## Initial Status

The service must establish:

```text
UNDER_REVIEW
```

through Domain behavior.

The caller must not be able to create an already-approved loan.

---

## Persistence

Persist through:

```text
LoanRepository
```

---

## Operation

Generate:

```text
OperationType.LOAN_APPLICATION
```

---

## Audit

Create the corresponding `AuditLog`.

The audit record must identify the relevant business operation and actor according to the Audit domain rules.

# 3. Evaluate Loan

## Description

Evaluates whether a Loan satisfies the Domain conditions necessary to proceed toward approval or rejection.

Evaluation should be conceptually separated from the actual state-changing approval or rejection operation.

---

## Input

```java
Loan evaluate(Loan loan);
```

or, when the evaluation is modeled as a decision:

```text
LoanEvaluationResult evaluate(Loan loan)
```

The latter is recommended if the evaluation must communicate a business decision without mutating the Loan.

---

## Status Validation

The Loan must be:

```text
UNDER_REVIEW
```

A Loan already:

```text
APPROVED
REJECTED
DISBURSED
CANCELLED
```

must not be evaluated as a new application.

---

## Customer Validation

Validate:

```text
Applicant exists
Applicant is ACTIVE
Applicant is eligible
```

---

## LoanType Validation

Validate:

```text
LoanType
```

and apply the policies associated with that type.

---

## Amount Validation

Validate:

```text
requestedAmount > 0
```

and all LoanType-specific amount constraints.

---

## Term Validation

Validate:

```text
termInMonths > 0
```

and all LoanType-specific term constraints.

---

## Interest Rate Validation

If an interest rate has already been established:

```text
interestRate >= 0
```

and the rate must satisfy LoanType-specific rules.

---

## Destination Account Validation

When applicable:

```text
AccountStatus == ACTIVE
```

and:

```text
Currency compatibility
AccountType compatibility
Ownership
```

must be evaluated.

---

## Evaluation Result

The Domain may produce:

```text
ApprovalDecision.APPROVED
ApprovalDecision.REJECTED
```

This is useful when evaluation itself does not mutate the Loan.

The recommended distinction is:

```text
Evaluate Loan
       │
       ▼
ApprovalDecision
       │
       ├── APPROVED ──► Approve Loan
       │
       └── REJECTED ──► Reject Loan
```

This avoids duplicating approval/rejection responsibilities.

---

# 4. Approve Loan

## Description

Approves a Loan that is currently under review.

The operation is restricted to:

```text
INTERNAL_ANALYST
```

## Input

```java
Loan approve(User user, Loan loan);
```

## User Validation

```text
user != null
user.status == UserStatus.ACTIVE
user.role == SystemRole.INTERNAL_ANALYST
```

---

## Customer Validation

Validate:

```text
loan.applicant != null
loan.applicant.status == CustomerStatus.ACTIVE
```

---

## Loan Status Validation

The authoritative Loan must be:

```text
UNDER_REVIEW
```

Only:

```text
UNDER_REVIEW → APPROVED
```

is permitted.

---

## LoanType Validation

Validate:

```text
loan.loanType != null
```

and all LoanType-specific approval rules.

---

## Requested Amount Validation

Validate:

```text
requestedAmount != null
requestedAmount > 0
```

---

## Approved Amount Validation

Validate:

```text
approvedAmount != null
approvedAmount > 0
```

Unless explicitly permitted:

```text
approvedAmount <= requestedAmount
```

---

## Interest Rate Validation

Validate:

```text
interestRate != null
interestRate >= 0
```

and the applicable LoanType constraints.

---

## Term Validation

Validate:

```text
termInMonths != null
termInMonths > 0
```

---

## Destination Account Validation

When applicable:

```text
destinationAccount != null
destinationAccount.accountStatus == ACTIVE
```

and:

```text
AccountType
Currency
Ownership
```

must satisfy the applicable rules.

## Approval Date

The Domain establishes:

```text
approvalDate
```

at the moment of the valid transition:


---

## Domain Behavior

The Loan Domain Model must execute a behavior equivalent to:

```text
loan.approve(...)
```

The Domain must verify the transition.

The application service must not simply execute:

```java
loan.setLoanStatus(LoanStatus.APPROVED);
```

without Domain transition rules.

---

## Persistence

Persist through:

```text
LoanRepository
```

---

## Operation

Generate:

```text
LOAN_APPROVAL
```

---

## Audit

Persist the corresponding audit record.

# 6. Disburse Loan

## Description

Disburses the approved Loan amount to the destination `BankAccount`.

This is a state-changing financial operation and therefore requires strict validation and transactional consistency.

---

## Input

The current conceptual input is:

```java
Loan disburse(Loan loan);
```

However, if the disbursement must be attributed to a human User, the recommended contract is:

```java
Loan disburse(User user, Loan loan);
```

The final decision depends on whether disbursement is:

```text
User initiated
```

or:

```text
System initiated
```

If system initiated, the audit model must explicitly represent the system actor.

---

## Loan Status Validation

The authoritative Loan must be:

```text
APPROVED
```

The only permitted transition is:

```text
APPROVED → DISBURSED
```

---

## Approved Amount Validation

Validate:

```text
approvedAmount != null
approvedAmount > 0
```

---

## Destination Account Validation

Validate:

```text
destinationAccount != null
```

and retrieve authoritative account information when necessary.

---

## AccountStatus Validation

The account must be:

```text
ACTIVE
```

The following states reject disbursement:

```text
BLOCKED
CLOSED
```

---

## AccountType Validation

The destination account must satisfy the applicable LoanType restrictions.

---

## Currency Validation

The currency of the Loan and BankAccount must be compatible.

Unless FX is explicitly supported:

```text
Loan.currency == BankAccount.currency
```

---

## Ownership Validation

The Domain must validate the relationship between:

```text
Loan.applicant
```

and:

```text
BankAccount.owner
```

when the business requires the destination account to belong to the applicant.

---

## Duplicate Disbursement Validation

A Loan must not be disbursed more than once.

The service must validate:

```text
LoanStatus != DISBURSED
```

and the authoritative persisted state must be checked.

The operation must also be protected against concurrent duplicate execution.

---

## BankAccount Domain Behavior

The service must not modify:

```text
BankAccount.currentBalance
```

directly through infrastructure.

The BankAccount Domain behavior responsible for receiving funds must be used.

Conceptually:

```text
Loan
 │
 ▼
Disburse Loan
 │
 ├── Validate Loan
 │
 ├── Validate BankAccount
 │
 ├── Credit BankAccount
 │
 └── Transition Loan
```

---

## Cross-Aggregate Consideration

`Loan` and `BankAccount` are separate Domain Models.

If they are separate Aggregates, the Loan service must not bypass BankAccount's business rules by directly modifying the BankAccount aggregate.

A preferred conceptual approach is:

```text
Loan Service
      │
      ▼
Bank Account application/domain operation
      │
      ▼
BankAccount
```

or an appropriate Domain Output Port representing the business capability required to credit the account.

The exact approach depends on whether Loan and BankAccount belong to the same bounded context.

---

## Disbursement Date

The Domain establishes:

```text

```

when the disbursement successfully occurs.

The caller must not provide this date.

---

## Transactional Consistency

The following changes must be consistent:

```text
Loan → DISBURSED
BankAccount → credited
Operation → LOAN_DISBURSEMENT
AuditLog → recorded
```

The system must prevent situations such as:

```text
Loan = DISBURSED
BankAccount = not credited
```

or:

```text
BankAccount = credited
Loan = APPROVED
```

The transaction strategy depends on the bounded-context architecture.

If all aggregates share one transactional boundary, a transaction may be used.

If they belong to different bounded contexts, an orchestration/event/outbox strategy may be required.

---

## Operation

Generate:

```text
LOAN_DISBURSEMENT
```

---

## Audit

Generate the corresponding audit event.

```text

                  │ disburse / cancel    │
                  └──────────┬───────────┘
                             │
             ┌───────────────┼────────────────┐
             │               │                │
             ▼               ▼                ▼
       LoanRepository  OperationRepository AuditRepository
             │               │                │
             └───────────────┼────────────────┘
                             ▼
                      Consistent Result
```

The essential architectural rule is:

```text
Domain Model
     ↓
Input Port
     ↓
Application Service
     ↓
Domain Validation + Domain Behavior
     ↓
Output Ports
     ↓
Adapters
```

and never:

```text
Controller
     ↓
Database
```

or:

```text
Service
     ↓
JPA / SQL / MongoDB
```

The Loan subdomain therefore remains aligned with:

```text
Hexagonal Architecture
        +
Domain-Driven Design
        +
Domain-first design
        +
Dependency Inversion
        +
High Cohesion
        +
Low Coupling
        +
Technology Independence
```
